# AI 营销工具 · PRD 规划（Claude Code Skill）

> 为「出海营销乙方 / 品牌方」的 AI coding 营销工具，产出**结构完整、可评审、可交开发**的 PRD。
> 沉淀自真实项目多轮评审打磨：写前先定**逻辑叙事**；按**对象/职能**分类功能模块（而非按角色）；**诚实标注**数据源授权与成本；内置**自我诊断评审表**防返工。

适用于：舆情雷达、品牌诊断、口碑&市场情报、竞品分析、社媒数据、选品/商机洞察等 **data / insight 类营销工具**的 PRD 撰写或重构。

## ✨ 特色

| 特色 | 说明 |
|---|---|
| 🧭 **逻辑叙事先行** | 动笔前先把"替谁、解决什么、为什么行业必须有、为什么我们做得了"讲成叙事，用户点头再成文 |
| 🗂️ **对象/职能轴模块** | 功能模块按 总览/收件箱/分析/报告/告警/设置 切，**不按用户角色切导航**（角色价值下沉为报告模板与订阅） |
| 🧩 **13 节标准骨架** | 定位→用户/痛点/分层→数据范围→市场空白→双向价值→商业模式闭环→功能模块→技术栈→算法→MVP→合规→数据契约→演进记录 |
| 💰 **低成本技术栈** | GitHub 可核验工具优先；官方 API 白嫖；抓取守合规；无授权即诚实标注，不假装自动化 |
| 🧱 **开源基座优先** | 动笔前先上 GitHub 找同类开源工具做底层基座/局部改造，避免从零造；并核实真实性(stars/license/最近提交)、许可证兼容、可借鉴点，再谈自研 |
| 🔁 **开发纠偏走查** | demo 出来后以目标用户视角走查 workflow/journey、对标真实竞品基础功能，挖盲区(P0/P1/P2)并出改造方案，防"做出来的是给懂技术的人用的产品" |
| 🩺 **评审自检清单** | "评审一份营销工具 PRD"变成可打勾的 checklist + 7 条模块反例自查 |

## 📦 安装

Skill 是一个目录：`skills/ai-marketing-tool-prd/`，内含 `SKILL.md`。

### 方式一：直接放入用户级 skills 目录（推荐）

```bash
git clone <本仓库地址> ai-marketing-tool-prd && cd ai-marketing-tool-prd
# 将 skill 目录链接到 Claude Code 用户级 skills
ln -s "$(pwd)/skills/ai-marketing-tool-prd" ~/.claude/skills/ai-marketing-tool-prd
```

或直接复制：

```bash
cp -r skills/ai-marketing-tool-prd ~/.claude/skills/
```

### 方式二：项目级使用

放到某项目的 `.claude/skills/ai-marketing-tool-prd/`，仅该项目可用。

### 验证

新开会话后输入 `/ai-marketing-tool-prd`，或在 `/skills` 中应能看到它。若看不到，重启 Claude Code。

> 本仓库也提供 `./install.sh` 一键安装到用户级。

## 🚀 使用

触发时机：

- 要为一款营销/AI 工具**从零写 PRD**；
- 已有 PRD 但**结构/命名/分类被评审打回**，需要按成熟标准重构；
- 需要**评审他人**的营销工具 PRD（跑一遍 §七 自检清单）。

产出：一份 13 节完整中文 PRD 文档（可直接入库、可评审、可交开发）。

## 📐 PRD 结构模板一览

| # | 节 | 回答的问题 |
|---|---|---|
| 0 | 头部 | 版本·日期·状态·一句话·关联文档 |
| 1 | 产品定位 | 它是谁、给谁、解决什么 |
| 2 | 用户画像·痛点·分层 | 谁、什么决策时刻、现在多痛（司机/乘客分层） |
| 3 | 监测/数据范围 | 采哪些平台、Owned vs 第三方、进哪个指标 |
| 4 | 市场空白 | 为什么行业必须有、差异位在哪 |
| 5 | 双向价值体系 | 对乙方 agency / 对品牌方各得什么 |
| 6 | 商业模式闭环 | 内部→增值→订阅→服务的路径 |
| 7 | 核心功能模块 | 对象/职能轴 IA + 指标(≤5/屏) + UI 灵感 |
| 8 | 技术栈 | 低成本对比表 + 数据源与授权（诚实） |
| 9 | 算法·规则·模型 | 公式 + 权重 + 判型 + 归因理由 |
| 10 | MVP 里程碑→验收口径 | 分阶段 + 可测出口 |
| 11 | 合规与风险 | 授权边界、抓取合规、平台政策变动 |
| 12 | 数据契约/示例 | 入库 JSON 对齐主引擎 |
| 13 | 演进记录 | 每版改了什么、为什么 |

## 🔧 两大能力

| 能力 | 阶段 | 内容 |
|---|---|---|
| **① 产品需求规划** | PRD 期 | 13 节骨架（见下表）：定位→用户/痛点/分层→数据范围→市场空白→双向价值→商业模式→功能模块→技术栈→算法→MVP→合规→契约→演进 |
| **② 开发过程校对纠偏** | demo 期 | 进入开发期后**自动嗅探触发**：目标用户视角走查 workflow/journey + 对标竞品基础功能 + 盲区分级(P0/P1/P2) + **自动输出《报告：开发纠偏走查报告与改造方案》** + 回写 PRD |

## 🧠 最易返工的 5 个坑（skill 已内置对策）

1. **按"角色"切导航** → 改成按对象/职能（总览/收件箱/分析/报告/告警/设置）；"给产品经理的那一页"是报告模板，不是 Tab。
2. **把工程管线当功能模块** → 采集/写回/调度/通知是"后台能力"，单列，不进用户模块表。
3. **数据源授权不诚实** → 无授权就写明哪些源做不了（如 Google Ads）；抓取标 ToS 灰区；付费源只做兜底。
4. **从零造轮子** → 动笔前先上 GitHub 找同类开源工具做底层基座/局部改造，并核实真实性、许可证、可借鉴点；没有才自研，且写明"为何不用现成的"。
5. **PRD 完整 ≠ 产品可用** → demo 出来必做目标用户视角走查，功能有但工作流入口断的，比缺功能更隐蔽。

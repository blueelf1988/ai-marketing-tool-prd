# AI 营销工具 · PRD 规划（自动 SOP）

## 一、先弄清楚：什么产品值得用本 skill

- 服务对象：**出海营销乙方（agency）内部用 / 给品牌方用的工具**（不是通用 C 端 App）。
- 典型：品牌势能诊断、品牌口碑&市场情报雷达、舆情监测、竞品分析、社媒数据、选品/商机洞察等。
- 它们共同点：① 输出"洞察/数据/分数"而非交易 ② 常见两个买方（乙方自用提升交付、品牌方直接订阅）③ 依赖外部平台数据（涉及授权/成本）。
- **不是**：纯内部效率脚本（无产品结构）、纯官网落地页（那是另一套打法）、交易型 SaaS 主流程（本 SOP 的"双向价值/市场空白"偏咨询服务语境）。

## 二、铁律（先读，防返工）

1. **写前先讲"逻辑叙事"**：用户要求 PRD 前，先用自然语言把"这个工具到底替谁、解决什么、为什么行业必须有、为什么我们做得了"讲成一段叙事，**确认后再成文**。叙事是 PRD 的脊柱。
2. **模块按"对象/职能"分类，不按"角色/人"**（最常犯的错）。
   - ❌ 口碑Tab=给运营、品牌Tab=给品牌总监、产品Tab=给PM、商机Tab=给CEO → 按角色切导航。
   - ✅ 总览 / 收件箱(逐条) / 分析(成组) / 报告(成品) / 告警(事件) / 设置 → 按用户面对的对象与动作切。
   - 角色价值**不删**，下沉为"报告模板 / 订阅 / 分析视角"（"给产品经理的那一页"是内容，不是导航）。
3. **同级互斥、单一切轴**：一个模块表只能用一把尺子切（都是对象，或都是职能）。别把"对象(产品) / 结果(商机) / 度量(口碑)"混进同一层。
4. **从属不设平级**：若 A 是 B 的一个度量/子集，别让 A、B 当兄弟 Tab（例：口碑 ⊂ 品牌）。
5. **名实相符**：装"回复/选题/待办"的页面（动作）别命名成"口碑"（结果）。
6. **工程管线 ≠ 功能模块**：采集、情感模型、写回引擎、调度、通知，是"后台能力"，用户不可见，单列一节，不进用户功能模块表。
7. **诚实标注授权与成本**：没有广告授权就明说哪些源做不了（如 Google Ads、Google 商家评价）；抓取类标 ToS 灰区；付费源做"兜底"而非默认；"数据源现状会变"给复验提示。
8. **开源基座优先，再谈自研**：写竞品分析/技术栈前，先上 GitHub 找同类开源工具做底层基座/局部改造，并核实真实性、许可证、可借鉴点（§4.4）。没有才自研且写明"为何不用现成的"。
9. **GitHub 工具可核验优先**：技术栈里列的 repo 要真名 + 主页链接 + 授权 + 一句"在本工具的角色"；写"查证日期"并提示实施前复验。
10. **每屏指标 ≤5**；每个相邻模块写明边界（做什么/不做什么）。
11. **每版记演进记录**：版本号 + 这一版为什么改（评审意见/自我诊断）。
12. **PRD 写完不是终点，demo 出来要走查**（§九）：以目标用户视角走查 workflow/journey、对标竞品基础功能，挖盲区、输出改造方案，回写 PRD。

## 三、标准 PRD 结构（模板）

按此 13 节成文（可用中文），每节标题给"这节回答什么 + 反例警示"：

| #  | 节                  | 回答                            | 反例 / 警示                 |
| -- | ------------------ | ----------------------------- | ----------------------- |
| 0  | 头部                 | 版本·日期·状态·一句话·关联文档             | 版本号缺失→后续评审对不上           |
| 1  | **产品定位**           | 它是谁、给谁、解决什么；与相邻工具边界           | 写成"XX管理系统"这种空话          |
| 2  | **用户画像 · 痛点 · 分层** | 谁、什么决策时刻、现在多痛；司机/乘客分层         | 只写"目标用户=营销人员"不写"一个决策时刻" |
| 3  | 监测/数据范围            | 采哪些平台、Owned vs 第三方、进哪个指标      | 漏了"要不要账号/授权"            |
| 4  | **市场空白**           | 为什么行业必须有、现在没人做                | 把"痛点"当"空白"；没讲差异位        |
| 5  | **双向价值体系**         | 对乙方 / 对品牌方各得什么                | 只写一方                    |
| 6  | **商业模式闭环**         | 从免费内部→增值→订阅→服务的路径             | 只有最终收费形态，没讲闭环           |
| 7  | **核心功能模块**         | 见 §四：导航 IA + 模块表 + 指标 + UI 灵感 | 见 §四反例                  |
| 8  | **技术栈**            | 低成本对比表 + 数据源与授权               | 列了不可核验/需授权的源还不标注        |
| 9  | **算法 · 规则 · 模型**   | 核心公式、权重、判型、归因理由               | 只给公式不给"为什么这么算"          |
| 10 | **MVP 里程碑 → 验收口径** | 分阶段；每阶段可测出口                   | 验收口径不可测（"体验好"）          |
| 11 | 合规与风险              | 数据合规、抓取边界、平台政策变动              | 只报喜不报忧                  |
| 12 | 数据契约 / 示例          | 入库 JSON 对齐主引擎                 | 字段漂移                    |
| 13 | 演进记录               | 每版改了什么、为什么                    | 无版本史→评审无法对比             |

> 用户若有既定结构清单，以用户清单为准套入本骨架。

## 四、核心功能模块规划（最容易返工，重点讲）

### 4.1 先给"IA 一图"（导航怎么走）

```
总览 ──→ 收件箱（逐条）──→ 分析（成组）──→ 报告（成品）──→ 分享/导出
  └── 告警（事件，独立触发）   监测设置（配置型）
```

- **总览**：打开第一屏，该看的已摆好（数字+风险+待办）。
- **收件箱**：每一条声音，可回复/标记。
- **分析**：自己探索，过滤/下钻，看模式。
- **报告**：成品，可订阅/导出/发给老板客户。
- **告警/设置**：事件 / 配置，不进探索主线。

### 4.2 模块表列法（每行）

`模块名 | 一句话边界 | 对象/职能 | 核心指标(≤5) | 主要使用者`

- **边界**用"做什么 / 不做什么"写死相邻混淆（总览vs分析vs报告是重灾区）。
- 每屏"一眼指标 ≤5"，写清"给谁、什么时候看"。

### 4.3 UI 可视化设计灵感

- 给设计语言（底色/圆角/强调色/语义色）+ 一个 **ASCII 线框** + 每张图"为什么这么画"。
- 数据域标签（Owned🏠/第三方🌐）贯穿，永不混。
- 图型与洞察匹配：趋势用面积/双轴、占比用 donut、优先级用 backlog、机会用象限/散点、证据用明细表（可回原文）。

### 4.4 竞品分析：**先上 GitHub 找开源基座，再谈自研**（v1.1 新增）

> 任何分析/竞品/技术栈要动笔前，**先去 GitHub 找有没有现成开源工具可做底层基座或局部改造，避免从零造**。这一步既是"竞品分析"（竞品里就有开源同类），也是"技术选型"的前置。

- **目的**：① 别重造轮子，开源能当基座/局部改造；② 顺便摸清竞品（开源同类 + 商业同类）；③ 把"差异化"讲清楚——我们不是做重复的轮子，而是补"归因/决策/交付"那一层。
- **搜什么**：产品名/同类名（social listening、brand monitoring、sentiment、review scraper…）、目标数据源（trustpilot scraper、youtube sentiment…）、GitHub Topic（`brand-monitoring` `sentiment-analysis`）、Claude Code skills 集合（marketing / SEO / data）。
- **核实三件套**（真实性与可借鉴点，缺一不可）：
  1. **真实性**：`stars` / `license` / **最近提交日期** / `open issues` 活跃度——死仓（>1 年没提交）当基座有风险，要标注。
  2. **许可证兼容**：MIT/Apache/BSD 免费商用；**GPL/AGPL 要警惕**（传染性，拿进商业产品要评估）。
  3. **可借鉴点**：它是整体基座、局部模块（某个采集器/某个评分/某个看板），还是只是参考思路？写清"拿来做什么"。
- **判据**：有合适的开源 → **基座/改造 + 我们补"归因与决策层"**；没有或不可靠 → 再谈自研，且在 PRD 里写明"为何不用现成的"。
- **诚实**：查证写日期（如 `2026-09 查证`）；工具状态会变，提示实施前复验 star/license/最近提交。

### 4.5 反例自查（评审别人的模块表，先查这 7 条）

1. 是不是用"人"当 Tab？（角色轴 → 改成对象/职能轴）
2. 同级吗？互斥吗？一把尺子吗？
3. 有没有从属当平级？（口碑⊂品牌）
4. 有没有把"动作"命名成"度量"？（回复页叫"口碑"）
5. 有没有把工程管线（采集/写回/调度）混进用户模块？
6. 首页/外壳 是否被当成模块在凑数？
7. 有没有先做 §4.4 开源基座扫描，还是直接从零规划？

## 五、逻辑叙事 → 成文的标准工作流

1. **问清本质**：工具到底替谁做哪个决定？（不是"监测什么"，是"让谁多快做个什么好决定"）
2. **讲叙事**：本质→现有工具哪三不管→差异化卡位→一句话定位。等用户点头。
3. **定边界**：与兄弟工具/引擎的边界（谁喂哪个指标、口径不变）。
4. **开源基座扫描（§4.4）**：上 GitHub 找同类开源工具可否做底层基座/局部改造 + 摸清竞品 + 核实真实性与可借鉴点——避免从零造，也把"差异化"讲清。
5. **成文**：按 §三模板写全（技术栈按 §六，含开源基座与核实）。
6. **评审驱动改版**：用户说"不对/复杂/命名错"时——**先自我诊断（用 §4.5 反例自查 + 反问自己"哪一层违反了哪条原则"）再改**，把诊断和改法都讲给用户，不要闷头重排。
7. 每版头部版本号 + §13 演进记录更新；README/主文档同步。
8. **demo 出来后走查（§九）**：开发出第一版可运行 demo，必做"目标用户视角走查"，挖盲区、出改造方案、回写 PRD。

## 六、低成本技术栈要点（营销数据工具特有）

1. **开源基座优先（§4.4）**：写技术栈前先在 GitHub 找同类开源工具——能当底层基座或局部改造的就别从零写；每个入选 repo 核实 **真实性(stars/license/最近提交/issue 活跃) + 许可证兼容 + 可借鉴点**，并标注查证日期。"整体基座"和"局部模块"要写清区别。
2. **能白嫖官方 API 就用官方**：YT Data API v3（1 万 units/日）、Trustpilot Business API、PRAW（Reddit 官方小量）、GDELT（新闻 keyless）。
3. **公开抓取只做低频单页**，守 robots、不反爬、不绕登录；Cookie 仅本地。
4. **需平台审核的接口**（FB/IG/TikTok 后台、Amazon）标"P2/未过审用公开兜底 + 低置信"，**不阻塞 P1**。
5. 没有授权就**砍掉或转人工**该数据源，诚实标注——不许假装自动化拿到。
6. 技术对比表列：工具(GitHub链接) | 类型 | 覆盖 | 授权/成本 | 在本工具角色 | **真实性/许可证/可借鉴点** | 注意。表尾给"全链路 ¥0、无广告授权"结论 + 查证日期 + "实施前复验"提示。

## 七、评审/验收自检清单（成文后过一遍）

## 九、开发过程中的校对纠偏：目标用户视角走查（v2 新增）

> 本节解决一个 PRD 写成后、开发进行中常见的问题：**PRD 写得再完整，开发出来也常是"给懂技术的人用的产品"，而不是"给目标用户用的产品"。** 差距不在功能，在目标用户的**工作流入口**没接进来。
>
> 本节**通用于任何工具类型**——不预设"运营/营销/社媒"等具体角色，也不预设具体竞品名单。所有示例均为**占位说明**，使用时应替换成本工具的真实目标用户、真实工作流、真实竞品。

### 9.1 什么时候用

PRD 进入开发、产出第一版可运行 demo/原型后，**必须**做一次"目标用户视角走查"。不是可选，是必做——它是 PRD 到可用产品之间的最后一道纠偏。

### 9.2 走查方法（三步）

**第一步：角色代入。** 抛弃"我设计了这些功能"的上帝视角，假设自己是那个每天要用这个工具完成本职工作的目标用户：

- 他第一天拿到工具，第一步做什么？他手里有什么**现成的东西**（数据、素材、既有工作产物）想直接拿进来用？
- 他每天的真实工作流是什么？（不是 PRD 里的理想流程，是现实的、带拖延和绕路的流程）
- 他遇到问题时，第一反应是查文档，还是点一下看反馈？

> 注意：这里的"目标用户"来自 PRD §2 的画像，不是临时假想。走查前先回头读一遍 PRD §2 的"决策时刻"和"痛点拆解"，把它们变成走查的对照清单。

**第二步：走完整 Journey。** 从"第一天打开"到"完成一个完整使用周期"逐环节走，每走一步对照"这个环节工具帮上忙了吗"。断点就是盲区。

> 下面几条是**通用检查维度**（不是具体工具的答案），每条都要结合本工具替换成具体场景：
>
> - **接入环节**：注册/授权/配置有没有即时反馈？失败/缺权限时用户知道"卡在哪、下一步点什么"吗？
> - **既有资产入口**：用户手头现成的东西（已有文件、已有数据、已有账号）能不能直接进工具，还是要重新造一遍？
> - **外部信息入口**：用户做这件事时习惯参考的外部信息（竞品、行情、案例、热点），工具里有没有入口，还是要切出去？
> - **即时反馈**：用户改一个东西，改完立刻知道"改对了还是改错了"吗？
> - **决策支撑**：用户的决策习惯（看趋势、看对比、看归因），工具答得上来吗？

**第三步：对标竞品。** 先列出本工具真实对标竞品的**基础功能模块清单**（不是抄竞品功能，是列出"用户认为理所当然该有的"那批基础件），逐项对照"我们有没有"。**缺的，几乎必然是盲区。**

> 竞品名单、基础模块清单都**由使用者在具体项目中现填**，不要照搬别的项目的例子。竞品/开源同类的搜寻与核实可复用 §4.4 的方法。

### 9.3 盲区的分级标准

| 级别     | 定义           | 判定             |
| ------ | ------------ | -------------- |
| **P0** | 会卡死用户，工具用不起来 | "缺了它，用户第一天就放弃" |
| **P1** | 用得起来但很痛苦     | "缺了它，效率打对折"    |
| **P2** | 体验瑕疵         | "缺了它，不致命但难受"   |

### 9.4 走查产出物

走查结束必须产出两份文档：

1. **走查报告**：盲区清单（按 P0/P1/P2 分级）+ 每条盲区的"用户真实诉求"+"对应竞品"。
2. **改造升级方案**：分批次改造（不碰红线的先做，碰红线的标注待确认），每批给验收口径。

### 9.5 铁律（走查时最容易犯的错）

1. **不能只查功能"有没有"，要查"用户能不能不查文档就用起来"。** 功能全有但入口断了的，比缺功能更隐蔽。
2. **红线不能因为"用户有诉求"就松。** 涉及合规/安全/不可逆操作的诉求（如抓取、自动花真金白银），用户再想要也不能硬做——走查发现这类诉求，要拆成"合规做法 + 折中入口"，而不是硬做。
3. **走查发现的盲区，必须回写 PRD。** 走查不是一次性动作，它的结论要变成 PRD 的迭代依据，否则下一版还会犯同样的错。
4. **不照搬别的项目的竞品名单和断点清单。** 每个工具的目标用户、工作流、竞品都不同，直接复用会漏掉本工具特有的盲区、或塞进无关的伪需求。

### 9.6 与 PRD 主流程的关系

```
PRD 规划（§一~§八）
      ↓
开发出第一版 demo
      ↓
目标用户视角走查（§九）← 本节
      ↓
发现盲区 → 改造升级方案 → 回写 PRD → 下一版开发
```

**一句话：PRD 负责"想清楚要做对什么"，目标用户视角走查负责"确认做出来的东西用户真能用"。两者缺一，工具都会停在"半成品闭环"。**

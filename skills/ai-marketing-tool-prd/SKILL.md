# AI 营销工具 · PRD 规划（自动 SOP）

为 **AI coding 的营销/品牌向工具**产出一份结构完整、可评审、可交开发的 PRD。以下是经过多轮真实评审打磨出的打法。

---

## 一、先弄清楚：什么产品值得用本 skill

- 服务对象：**出海营销乙方（agency）内部用 / 给品牌方用的工具**（不是通用 C 端 App）。
- 典型：品牌势能诊断、品牌口碑&市场情报雷达、舆情监测、竞品分析、社媒数据、选品/商机洞察等。
- 它们共同点：① 输出"洞察/数据/分数"而非交易 ② 常见两个买方（乙方自用提升交付、品牌方直接订阅）③ 依赖外部平台数据（涉及授权/成本）。
- **不是**：纯内部效率脚本（无产品结构）、纯官网落地页（那是另一套打法）、交易型 SaaS 主流程（本 SOP 的"双向价值/市场空白"偏咨询服务语境）。

---

## 二、铁律（先读，防返工）

1. **写前先讲"逻辑叙事"**：用户要求 PRD 前，先用自然语言把"这个工具到底替谁、解决什么、为什么行业必须有、为什么我们做得了"讲成一段叙事，**确认后再成文**。叙事是 PRD 的脊柱。
2. **模块按"对象/职能"分类，不按"角色/人"**（最常犯的错）。
   - ❌ 口碑Tab=给运营、品牌Tab=给品牌总监、产品Tab=给PM、商机Tab=给CEO → 按角色切导航。
   - ✅ 总览 / 收件箱(逐条) / 分析(成组) / 报告(成品) / 告警(事件) / 设置 → 按用户面对的对象与动作切。
   - 角色价值**不删**，下沉为"报告模板 / 订阅 / 分析视角"（"给产品经理的那一页"是内容，不是导航）。
3. **同级互斥、单一切轴**：一个模块表只能用一把尺子切（都是对象，或都是职能）。别把"对象(产品) / 结果(商机) / 度量(口碑)"混进同一层。
4. **从属不设平级**：若 A 是 B 的一个度量/子集，别让 A、B 当兄弟 Tab（例：口碑 ⊂ 品牌）。
5. **名实相符**：装"回复/选题/待办"的页面（动作）别命名成"口碑"（结果）。
6. **工程管线 ≠ 功能模块**：采集、情感模型、写回引擎、调度、通知，是"后台能力"，用户不可见，单列一节，不进用户功能模块表。
7. **诚实标注授权与成本**：没有广告授权就明说哪些源做不了（如 Google Ads、Google 商家评价）；抓取类标 ToS 灰区；付费源做"兜底"而非默认；"数据源现状会变"给复验提示。
8. **GitHub 工具可核验优先**：技术栈里列的 repo 要真名 + 主页链接 + 授权 + 一句"在本工具的角色"；写"查证日期"并提示实施前复验。
9. **每屏指标 ≤5**；每个相邻模块写明边界（做什么/不做什么）。
10. **每版记演进记录**：版本号 + 这一版为什么改（评审意见/自我诊断）。

## 三、标准 PRD 结构（模板）

按此 13 节成文（可用中文），每节标题给"这节回答什么 + 反例警示"：

| # | 节 | 回答 | 反例 / 警示 |
|---|---|---|---|
| 0 | 头部 | 版本·日期·状态·一句话·关联文档 | 版本号缺失→后续评审对不上 |
| 1 | **产品定位** | 它是谁、给谁、解决什么；与相邻工具边界 | 写成"XX管理系统"这种空话 |
| 2 | **用户画像 · 痛点 · 分层** | 谁、什么决策时刻、现在多痛；司机/乘客分层 | 只写"目标用户=营销人员"不写"一个决策时刻" |
| 3 | 监测/数据范围 | 采哪些平台、Owned vs 第三方、进哪个指标 | 漏了"要不要账号/授权" |
| 4 | **市场空白** | 为什么行业必须有、现在没人做 | 把"痛点"当"空白"；没讲差异位 |
| 5 | **双向价值体系** | 对乙方 / 对品牌方各得什么 | 只写一方 |
| 6 | **商业模式闭环** | 从免费内部→增值→订阅→服务的路径 | 只有最终收费形态，没讲闭环 |
| 7 | **核心功能模块** | 见 §四：导航 IA + 模块表 + 指标 + UI 灵感 | 见 §四反例 |
| 8 | **技术栈** | 低成本对比表 + 数据源与授权 | 列了不可核验/需授权的源还不标注 |
| 9 | **算法 · 规则 · 模型** | 核心公式、权重、判型、归因理由 | 只给公式不给"为什么这么算" |
| 10 | **MVP 里程碑 → 验收口径** | 分阶段；每阶段可测出口 | 验收口径不可测（"体验好"） |
| 11 | 合规与风险 | 数据合规、抓取边界、平台政策变动 | 只报喜不报忧 |
| 12 | 数据契约 / 示例 | 入库 JSON 对齐主引擎 | 字段漂移 |
| 13 | 演进记录 | 每版改了什么、为什么 | 无版本史→评审无法对比 |

> 用户若有既定结构清单，以用户清单为准套入本骨架。

## 四、核心功能模块规划（最容易返工，重点讲）

### 4.1 先给"IA 一图"（导航怎么走）
```
总览 ──→ 收件箱（逐条）──→ 分析（成组）──→ 报告（成品）──→ 分享/导出
  └── 告警（事件，独立触发）   监测设置（配置型）
```
- **总览**：打开第一屏，该看的已摆好（数字+风险+待办）。
- **收件箱**：每一条声音，可回复/标记。
- **分析**：自己探索，过滤/下钻，看模式。
- **报告**：成品，可订阅/导出/发给老板客户。
- **告警/设置**：事件 / 配置，不进探索主线。

### 4.2 模块表列法（每行）
`模块名 | 一句话边界 | 对象/职能 | 核心指标(≤5) | 主要使用者`
- **边界**用"做什么 / 不做什么"写死相邻混淆（总览vs分析vs报告是重灾区）。
- 每屏"一眼指标 ≤5"，写清"给谁、什么时候看"。

### 4.3 UI 可视化设计灵感
- 给设计语言（底色/圆角/强调色/语义色）+ 一个 **ASCII 线框** + 每张图"为什么这么画"。
- 数据域标签（Owned🏠/第三方🌐）贯穿，永不混。
- 图型与洞察匹配：趋势用面积/双轴、占比用 donut、优先级用 backlog、机会用象限/散点、证据用明细表（可回原文）。

### 4.4 反例自查（评审别人的模块表，先查这 6 条）
1. 是不是用"人"当 Tab？（角色轴 → 改成对象/职能轴）
2. 同级吗？互斥吗？一把尺子吗？
3. 有没有从属当平级？（口碑⊂品牌）
4. 有没有把"动作"命名成"度量"？（回复页叫"口碑"）
5. 有没有把工程管线（采集/写回/调度）混进用户模块？
6. 首页/外壳 是否被当成模块在凑数？

## 五、逻辑叙事 → 成文的标准工作流

1. **问清本质**：工具到底替谁做哪个决定？（不是"监测什么"，是"让谁多快做个什么好决定"）
2. **讲叙事**：本质→现有工具哪三不管→差异化卡位→一句话定位。等用户点头。
3. **定边界**：与兄弟工具/引擎的边界（谁喂哪个指标、口径不变）。
4. **成文**：按 §三模板写全。
5. **评审驱动改版**：用户说"不对/复杂/命名错"时——**先自我诊断（用 §4.4 那 6 条 + 反问问自己"哪一层违反了哪条原则"）再改**，把诊断和改法都讲给用户，不要闷头重排。
6. 每版头部版本号 + §13 演进记录更新；README/主文档同步。

## 六、低成本技术栈要点（营销数据工具特有）

1. **能白嫖官方 API 就用官方**：YT Data API v3（1 万 units/日）、Trustpilot Business API、PRAW（Reddit 官方小量）、GDELT（新闻 keyless）。
2. **公开抓取只做低频单页**，守 robots、不反爬、不绕登录；Cookie 仅本地。
3. **需平台审核的接口**（FB/IG/TikTok 后台、Amazon）标"P2/未过审用公开兜底 + 低置信"，**不阻塞 P1**。
4. 没有授权就**砍掉或转人工**该数据源，诚实标注——不许假装自动化拿到。
5. 技术对比表列：工具(GitHub链接) | 类型 | 覆盖 | 授权/成本 | 在本工具角色 | 注意。表尾给"全链路 ¥0、无广告授权"结论 + 查证日期。

## 七、评审/验收自检清单（成文后过一遍）

- [ ] 一句话定位能在 30 秒讲清"替谁做什么决定"
- [ ] 逻辑叙事先行且用户点头过
- [ ] 用户画像里有"一个具体决策时刻"而非泛泛人群
- [ ] 分层用了"司机/乘客"（操作者 vs 决策者）而非纯角色堆叠
- [ ] 市场空白讲清"为什么行业必须有 + 差异位"（非把痛点当空白）
- [ ] 双向价值（乙方/品牌方）都覆盖
- [ ] 商业模式有从内到外的闭环路径，不是只挂最终价
- [ ] 功能模块通过 §4.4 反例自查 6 条
- [ ] 相邻模块边界写清；每屏指标 ≤5
- [ ] 后台能力与用户功能分开列
- [ ] 技术栈可核验、授权/成本诚实、有查证日期
- [ ] 算法给了公式也给归因理由
- [ ] MVP 验收口径可测（分数/条数/误差范围）
- [ ] 合规与风险诚实（含"哪些源做不了/要授权"）
- [ ] 版本号 + 演进记录在

## 八、参考案例

`brand-power-diagnostic/` 项目（Claude-Projects 下）是本法反复打磨的活样本：
- `06-口碑测评子工具-PRD.md` —— 舆情→情报→品牌口碑&市场情报雷达，历经 v0.2(公关)→v0.3(决策情报)→v0.4(双域+社媒运营)→v0.5(旅程化)→v0.6(对象/职能轴)。**最能学的是 §13 演进记录**：每一版都写了"为什么错、怎么改"。
- `07-评价社媒子工具-PRD.md` —— 姊妹工具（评价分/粉丝/渗透），体现"与 A 的边界"写法。
- `05-技术栈总览.md` —— 技术栈唯一口径 + 与各 PRD 的引用关系。
- 读取它们理解：逻辑叙事先行、双域(Owned/第三方)不混、对象/职能轴模块、诚实授权标注、GitHub 可核验、演进记录。
